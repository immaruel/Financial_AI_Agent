# 02. Query Understanding and Retrieval Policy

## 1. Purpose

Turn the user's natural-language query into an LLM-drafted interpretation (`QuerySpecDraft`), then have deterministic code validate and finalize it into a `QuerySpec`. From there, translate the `QuerySpec` into an executable `RetrievalPolicy` (retrieval channels, budget, retry count).

From a harness engineering perspective, these two stages are the **first failure-localization point in the online pipeline**. Retrieval and claim-verification quality downstream depend heavily on the quality of the QuerySpec/Policy, so both must always be subject to trace and verification metrics.

---

## 2. Query Understanding Agent

### 2.1 Role Boundary

The LLM does not answer the question. It only produces a `QuerySpecDraft` JSON. The following are things the LLM never does.

- Produce a canonical entity ID (only the `surface` form is extracted)
- Choose a retrieval tool name
- Guess a time range when no temporal expression is present (`time.kind` stays `"unspecified"`)
- Decide `as_of` on its own (it always equals the server-supplied `request_timestamp`)

### 2.2 System Prompt

```text
You are the Query Understanding Agent that builds the retrieval plan for a
financial research query.

Goal:
Do not answer the user's question. Extract the question's intent and the
evidence types it requires, formatted to the given JSON Schema.

Rules:
1. Do not invent company facts, recent information, numbers, or relationships
   beyond what the question states.
2. For entities, extract only the surface form from the question, not a
   canonical ID.
3. If there is no temporal expression, keep time.kind as "unspecified" and do
   not estimate a period.
4. Set as_of to exactly the provided request_timestamp.
5. graph_relation is required when relationships, paths, propagation, or
   multi-hop reasoning are central to the question.
6. primary_source_quote is required when management commentary, filing
   wording, or a direct source is central to the question.
7. numeric_value is required when an amount, ratio, growth rate, financial
   figure, or period comparison is needed.
8. table_or_figure is required when a table, chart, row/column, quarterly
   value, or visual asset is needed.
9. Use only required, preferred, or not_needed for each need.
10. Do not answer the question or select a retrieval tool name.
11. Do not output fields or explanatory text outside the JSON Schema.
```

The user message is built from `request_timestamp`, `user_query`, and the `QuerySpecDraft` JSON Schema generated by Pydantic (`_build_user_prompt` in `agent/query_understanding.py`).

### 2.3 QuerySpecDraft Example

```json
{
  "query_id": "q_...",
  "original_query": "How did Samsung Electronics' CFO explain the recent margin decline?",
  "request_timestamp": "2026-08-07T10:00:00+09:00",
  "as_of": "2026-08-07T10:00:00+09:00",
  "entities": [{"surface": "Samsung Electronics", "suspected_type": "company"}],
  "intent": "management_explanation",
  "sub_intents": [],
  "question_focus": ["margin_decline_cause"],
  "time": {"kind": "relative", "expression": "recent"},
  "answer_format": "explanation_with_citations",
  "evidence_needs": {
    "graph_relation": "not_needed",
    "primary_source_quote": "required",
    "numeric_value": "not_needed",
    "table_or_figure": "not_needed"
  },
  "memory_mode": "if_relevant",
  "confidence": 0.93
}
```

### 2.4 Failure Handling (`QueryUnderstandingAgent.understand()`)

```text
1. Call the LLM -> schema/field validation
2. On failure -> request one repair pass that includes the validation_error
3. On repeated failure -> build a rule-based, deterministic fallback QuerySpecDraft
   (validation_status = "planner_fallback")
4. If an entity remains ambiguous -> validation_status = "entity_ambiguous"
```

The fallback draft is built only from the `_GRAPH_PATTERNS`/`_QUOTE_PATTERNS`/`_NUMERIC_PATTERNS`/`_TABLE_PATTERNS` regular expressions and the known entity dictionary; it never adds a surface form absent from the query.

## 3. Deterministic Validation: `QuerySpecValidator`

The LLM output is only a draft. Everything below is finalized by code (`agent/query_understanding.py`).

### 3.1 NeedLevel Correction

A plain `true/false` cannot distinguish "absolutely required" from "helpful if available," so a three-level enum is used.

```python
class NeedLevel(str, Enum):
    REQUIRED = "required"
    PREFERRED = "preferred"
    NOT_NEEDED = "not_needed"
```

If explicit keyword signals are present (relationship/supply-chain/propagation wording for `graph_relation`; management-commentary wording for `primary_source_quote`; amount/ratio wording for `numeric_value`; table/chart wording for `table_or_figure`), the field is promoted to `required` regardless of the LLM's value; if no signal is present at all, `graph_relation`/`table_or_figure` are demoted to `not_needed`. For a policy/industry/company propagation question where `graph_relation` is `required`, `primary_source_quote` is also promoted to `required`, so temporal adjacency in the graph alone is never treated as a supported causal claim.

### 3.2 Entity Resolution

`DeterministicEntityResolver` uses only the `entity_dict` (company/industry/institution/region/commodity alias → canonical ID) supplied by the application. A surface form the LLM proposes is discarded if it is not actually present in the query text (`entity_not_in_query`); any dictionary alias the LLM missed is deterministically added back. Multiple candidates yield `ambiguous`; no dictionary match yields `unresolved`.

### 3.3 Intent / Sub-intent Normalization

Intent is recomputed after `evidence_needs` is finalized — `graph_relation=required` maps to `relationship_lookup`/`impact_analysis`, `primary_source_quote=required` maps to `management_explanation`, `table_or_figure=required` maps to `document_visual_lookup`, `numeric_value=required` maps to `numeric_lookup`, and so on. Any intent string the LLM proposed is discarded if it conflicts with these rules.

### 3.4 Temporal Expression Parsing

Year ranges, explicit dates (including ranges), quarters (`2026Q1`), months, and relative expressions ("the last 3 quarters," "last quarter," "this year," etc.) are parsed with regular expressions into `from_date`/`to_date` or preserved as a relative `value`. **If there is no temporal expression, `time.kind` stays `"unspecified"` — the system never fills in an arbitrary 30-/90-day default window.**

### 3.5 Fixing `as_of`

`as_of` is always the `request_timestamp` the server received. It is never replaced by the LLM's guess or by re-reading "the current time" during execution, so the same query can be reproduced and verified against the same reference point at any later time.

## 4. Retrieval Policy Builder

`RetrievalPolicyBuilder` (`agent/routing.py`) never calls an LLM. It maps the NeedLevel values in `QuerySpec.evidence_needs` to a channel set using code rules.

```python
if graph_required or (graph_preferred and include_preferred):
    channels.add("graph")
if quote_required:
    channels.update({"lexical", "vector"})
if numeric_required:
    channels.update({"lexical", "vector", "document_block"})
if table_required:
    channels.add("document_block")
if not channels:
    channels.update({"lexical", "vector"})   # default to text-first hybrid when nothing is explicit
```

`preferred` channels are enabled only when `assurance_mode = "high_assurance"`; they are skipped in `fast` mode. Graph can be the sole channel only for a pure relationship lookup (`graph_required` and none of quote/numeric/table are needed) — otherwise, even when graph finds relationship candidates, hybrid retrieval still confirms them against the source text.

### 4.1 Route by Question Type

| Question characteristic | Primary path | Secondary path | Role of the graph |
|---|---|---|---|
| How did management explain a cause | hybrid (lexical + vector → RRF → rerank) | — | Not used |
| The value in a specific figure or table | hybrid + document_block | — | Not used |
| Multi-step relationships among companies/industries/policy | graph | Hybrid expansion of the documents the graph found | Primary path for relationship traversal |
| How a policy's impact propagates through an industry to companies | graph + hybrid | — | Graph relation/temporal structure + hybrid source text |
| Fact-checking a news article or filing | hybrid | — | Used only to link candidate relations, if at all |

### 4.2 RetrievalPolicy Example

```json
{
  "policy_id": "rp_...",
  "channels": ["lexical", "vector"],
  "graph_mode": "off",
  "source_filters": ["filing", "earnings_transcript"],
  "date_filter": {"published_at_lte": "2026-08-07T10:00:00+09:00"},
  "fusion": "rrf",
  "embedding_model": "BAAI/bge-m3",
  "reranker": "BAAI/bge-reranker-v2-m3",
  "evidence_budget": 18,
  "retry_budget": 2,
  "assurance_mode": "high_assurance",
  "selected_by": "deterministic_policy_v2_two_clock"
}
```

`source_filters` is decided from query keywords (tariff/policy/regulation → `government`; CFO/earnings call → `filing` + `earnings_transcript`, etc.), and `evidence_budget`/`retry_budget` are set smaller in `fast` mode.

### 4.3 Two Clocks

`date_filter` keeps the publication time and the business/event period as two separate clocks.

- `published_at_lte` — answers "could the system have known this as of T?" Always anchored to `as_of`.
- `effective_at_gte/lte` — the business/event period the question actually asks about. Using the requested fiscal period as `published_at_gte` would drop later-filed source documents covering that same period, so the two are never merged.
- A relative expression (`relative_value`, e.g. `last_4_quarters`) is interpreted differently by `relative_clock` (`publication`/`effective`/`best_available`) — news is anchored to publication time, earnings/filings to the business period.

## 5. User Memory: Only Its Activation Is Decided Here

`QuerySpec.memory_mode` (`off`/`if_relevant`/…) is drafted by the Query Understanding Agent, and if the query contains an explicit request such as "don't use memory," validation forces it to `off` (`memory_explicitly_disabled`). The actual memory-selection logic is described in [06_recovery_memory_and_harness.md](06_recovery_memory_and_harness.md).

## 6. Verification Points from a Harness Perspective

| Item | Meaning |
|------|---------|
| `intent classification accuracy` | Was the query intent classified correctly? |
| `entity phrase extraction / resolution accuracy` | Were key company/industry/policy expressions captured and resolved to the correct canonical ID? |
| `temporal constraint extraction accuracy` | Were explicit/relative time expressions parsed correctly, without inventing a period? |
| `evidence_needs judgment accuracy` | Does the LLM draft plus code correction match what the question actually requires? |
| `policy channel selection accuracy` | Do the selected channels match the required evidence types? |

Trace should include at minimum: the raw/normalized query, the full `QuerySpec` (as JSON), `validation_notes` (reasons for promotion/demotion/removal), and the resulting `RetrievalPolicy`.

Representative failure types: F1 entity confusion, F2 temporal error, F8 over-defensiveness (unnecessary clarification).

---

## 7. Design Rationale

**Why combine LLM structured output with deterministic validation?**
Questions like "how did management explain the cause," "compare the figures in the table," or "show me the relationship path" are hard to route reliably with a keyword dictionary alone. Canonical entities, `as_of`, and channel mapping, on the other hand, need reproducibility, so code owns them. This is exactly where the boundary is drawn so the LLM's free text never directly decides a tool call.

**Why is `evidence_needs` three-valued instead of boolean?**
A binary value cannot distinguish "mandatory" from "nice to have," so when budget is constrained there is no way to prioritize. `preferred` gives room to selectively execute a channel depending on `fast` vs. `high_assurance` mode.

**Why separate publication time from the business period?**
For a question with an explicit accounting period ("the last four quarters' revenue"), filtering by publication time alone would drop a late-filed correction; filtering by business period alone risks leaking information not yet publicly disclosed.
